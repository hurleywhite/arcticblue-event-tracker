## What this project is

A single-page event tracker for ArcticBlue's internal team. Lists every in-person AI conference between now and end of 2026, sorted into TODAY / UPCOMING / ARCHIVED. Built from a `.docx` source doc, deployed to Vercel.

## Who this is for

- **Internal users:** Thor (CEO) + the ArcticBlue ops team. They open the page on a laptop or phone to decide which events to attend.
- **External link target:** the page also lives at a public Vercel URL so it can be shared in Slack / email / docs.

## The seven rules

### Rule 1 — Single self-contained HTML file
The deploy target is `public/index.html`. Inline CSS, inline JS, no external bundles, no React, no Next.js, no Tailwind. The page must work when opened locally with `file:///`. Web fonts from Google Fonts are fine; everything else lives in-file.

### Rule 2 — No hallucinated URLs (the most important rule)
Every event card that links somewhere must link to a URL that exists in one of these two files:
- `data/event-urls-from-doc.json` — extracted from the source `.docx`'s hyperlinks by `src/extract-urls.py`
- `data/event-urls-manual.json` — manually added by a human after visiting the page in a browser

If neither file has a URL for an event, the card stays **non-clickable**. Do not invent URLs by guessing the event website ("looks like raisesummit.com"). Do not generate URLs from event names. The user explicitly called this rule out as part of best practices.

### Rule 3 — Source of truth is the .docx
Events come from `data/ArcticBlue AI 2026 Event Tracker.docx`. Do not fork the event list into a separate JSON / YAML file. If you need to add an event, add it to the doc and rerun `build.py`. If you need to change an event's date, change it in the doc and rerun.

### Rule 4 — White-primary aesthetic for internal tools
The page is **white background, black text, gray rules**. Sparing use of one accent blue (`#2773c2`, pulled from the ArcticBlue logo's middle band). High-priority badges use solid black on white for maximum contrast. Do not pivot to dark mode unless the user explicitly asks.

ArcticBlue's *marketing* site (`arcticblue.ai`) is dark with periwinkle accents — that's a different visual register for external work. Internal tools follow the joes-fac / whatcameoutinai pattern: clean white, monochrome.

### Rule 5 — Mobile responsive
The KPI grid must collapse from 4 columns to 2 columns under 800px. Filters stack vertically under 600px. Cards stack to a single column. Tap targets must be at least 44×44 px (input fields, buttons, select dropdowns). The archive section uses `<details>` for collapse — never JavaScript-driven toggle.

### Rule 6 — Build-time generation, not runtime
The page is generated by `build.py` at build time. The "today" date is the build-script's idea of today. There is no client-side data fetching. If you want real-time refresh, the answer is "run the build on a daily cron and redeploy" — not "load events via JS on page load."

### Rule 7 — Fonts and brand assets
- Body font: **Hanken Grotesk** (Google Fonts) — 400, 500, 600, 700, 800
- Mono font: **Fragment Mono** (Google Fonts) — used for dates, numbers, badges, eyebrows
- Logo: `public/arcticblue-logo.png` — the real ArcticBlue logomark in three blues + gray. Don't replace with a generic gradient or a typographic mark.
- Primary accent: `#2773c2` (the logo's middle blue)
- Background: `#ffffff`
- Foreground: `#0a0a0a`
- Rule lines: `#e7e7e8`

## Common requests and how to handle them

### "Add a verified URL for event X"
1. Open `data/event-urls-manual.json`
2. Add `"NN": "https://verified-url.com/"` where NN is the event number
3. Rerun `python3 src/build.py`
4. Visually confirm the card now has the ↗ arrow
5. Commit

### "Update the source doc with a new event"
1. Update `data/ArcticBlue AI 2026 Event Tracker.docx` directly
2. Rerun `python3 src/extract-urls.py` (in case the new event has a hyperlink)
3. Rerun `python3 src/build.py`
4. Spot-check the page

### "Add a calendar view"
1. Don't replace the existing grid — add a view toggle
2. Each event card already has `data-start-date` (or could — see `build.py`); reuse for calendar positioning
3. Calendar grid in CSS (no library); event chips inside day cells
4. Mobile: stack one month per screen vertically
5. The view-toggle state lives in `localStorage` so it persists between visits

### "Change the brand color"
The default is `#2773c2`. To change it, update the `--ab-blue` CSS variable in one place inside `build.py`. Don't search-and-replace across the file — keep the variable as the single source.

### "Make the cards open in the same tab"
Default is `target="_blank" rel="noopener"`. Removing `target="_blank"` is fine if the user explicitly asks. Don't add `target="_self"` redundantly — just remove the attribute.

## What NOT to do

- **Don't invent URLs.** This is the hard rule. If unsure, ask before assuming.
- **Don't add a build chain.** No webpack, no Vite, no Next.js conversion. The point of this project is that it's trivially deployable.
- **Don't add tracking.** No Google Analytics, no Plausible, no Cloudflare Web Analytics, no Vercel Analytics unless explicitly requested.
- **Don't load anything from third-party CDNs except Google Fonts.** The brand-integrity rule from HRF carries over: external dependencies are surface area for outages and supply-chain attacks.
- **Don't break the no-`<style>`-on-elements rule lightly.** All styling lives inside one `<style>` block at the top — no inline `style=...` on individual elements except where dynamic (the existing JS-controlled `style.display = 'none'` for filtering is acceptable).
- **Don't change the layout to a sidebar / two-column without asking.** Single-column flow is intentional; works on every screen size.

## How the user evaluates "is this good?"

Three questions:

1. **"Did you invent any URLs?"** If yes, the work is rejected, no matter how good the page looks.
2. **"Does it look amazing?"** Aesthetic quality matters. The page is a touchpoint that gets shared internally and externally — sloppy typography or weak hierarchy will be noticed.
3. **"Does it work on mobile?"** Open on a phone, no horizontal scroll, all tap targets reachable, filters usable.

If all three are yes, the work passes.
